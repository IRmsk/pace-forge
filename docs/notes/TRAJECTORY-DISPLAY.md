## 硬证据（可复现）

### 1. 详情接口不回传轨迹点

50 条历史记录逐条拉 `POST /api/v70260/runnings/get_one_record`，结果一致：

| 字段 | 值 | 条数 |
|---|---|---|
| `allLocJson` | `null` | 50 / 50 |
| `jsonFromObs` | `1` | 50 / 50 |
| `fivePointJson` | `""` | 50 / 50 |

其中包括用 Neko 刷的 19 条（`avgPower` 184~266 非零，能认出来）和 pace 刷的 31 条。
**所以「服务端不回过轨迹点」与用哪个工具无关**，这点可以确定。

### 2. 轨迹对象确实在 OBS 里

`run_data/{rrid/1000000}/{rrid}.json` 用 `/api/obs/temporary/url` 换 Get 签名可下载：

```
rrid 1360341003 → 200，解 gzip 后 423 个点，每点 28 字段
```

所以「轨迹没上传」这个假设可以排除。

### 3. objectKey 的时区，实测分布

| 来源 | 条数 | UTC+8 key | UTC key | rrid key |
|---|---|---|---|---|
| pace 新版 | 3 | **3/3 在** | 3/3 | 3/3 |
| Neko | 19 | **19/19 在** | 0/19 | 0/19 |
| pace 旧版 | 28 | 部分 404（11-07 那批 10+ 条全 404） | 多数在 | 28/28 在 |

`run_data/{YYYYMMDDHH}/{uuid}.json` 里的 `HH` 按设备时区（UTC+8）算，这一点由
Neko 全量命中反证——它只传 UTC+8 这一份，且从未 404。

### 4. App 的分支判断（smali）

`RunHistoryDetailPImpl$requestSportRecord$1$...$map$1$2.smali:232-284`：

```kotlin
if (detailBean.jsonFromObs == 1) {
    RunDataUploadManger.OooO(uuid, uid, ...)
}
```

`getJsonFromObs()` 没有 setter（`grep -rn setJsonFromObs` 零命中），客户端控制不了。

`OooO` → `$queryUUID$2.smali` 查 `getRunDataDao().OooO0OO(uuid, uid)`，即本地 Room；
`entity == null` 时直接返回空。**这段反编译里没有看到网络回退**。

### 一条来源未记录的观察，不算证据

2026-11-10 首次看修复效果时，反馈是「有了」，但当时没记下看的是哪个客户端。
而这两个客户端的含义正好相反：

| 在哪看的 | 对候选 B 的判别力 |
|---|---|
| App 详情页 | **当场排除候选 B**（B 的预测就是无线），剩下只是「机制没查清」 |
| Web 详情页（本工具自己的页面） | **零判别力**。那条线是网页自己从 OBS 拉的（`/api/obs/fetch` + `DecompressionStream` 解 gzip），App 走哪条取数路径完全没被触及 |

所以这条观察目前的强度是「来源不明」：不能拿来支持 A，也不能拿来否定 B。
如果不记录来源就去做判定实验，做完还是同一个问题——上次就是这么把
「Web 端看到线」写成了「App 里出了线」，进而把候选 A 写成结论。

## 未定项（待定）：App 到底会不会去 OBS 拉

第 4 条和「用户观察到新记录有线」不能同时成立。两个候选：

**候选 A —— App 会拉 OBS。** 第 4 条只覆盖了一条分支（`jsonFromObs == 1` 且本地
无文件时走 `OooO`），但 `OooO` 内部或调用方可能还有一层「本地没有就用 objectKey
去 OBS 取」，反编译没跟到底。若成立，则 key 齐全（本次修复）就是有线的原因，
旧记录 11-07 那批 UTC+8 key 404 正是它们没线的原因。

**候选 B —— App 只读本地。** 那么无论 key 怎么样都不会有线，用户看到的线来自
别的路径（例如看的是 Web 端详情页，或记混了记录）。本次对报文的三处修正
（`allLocJson` 空串、五点补 `isPass/state/id/flag`、`fixed_point_json` 改 envelope）
解决的只是**服务端判定**（点位规则从 false 变 true），跟画线无关。

**两个候选都没有做过来源明确的对照实验，所以不下结论。** 上一版文档直接断言
B，`c2485e4` 的 commit message 直接断言 A，两者都是过度断言；而替代它们的
那条「看到线」的观察又没记录客户端，同样不足以判定。

## 判定实验（两条记录，两分钟）

| rrid | 时间 | UTC+8 key | 若 A 成立 | 若 B 成立 |
|---|---|---|---|---|
| `1360341003` | 11-10 15:36 | 存在 | **有线** | 无线 |
| `1358389153` | 11-07 20:00 | 404 | 无线 | 无线 |

**必须记下在哪个客户端看的。** 同一份记录在 App 和 Web 详情页的渲染走的是
两套完全独立的代码，看错地方等于没做实验。

在 App 详情页点开 `1360341003`：

- 有线 → 候选 A，本次修复即根因，之后刷的记录都该有线
- 无线 → 候选 B（此时不要马上去 Web 页验证——Web 端必然是有的，那只说明网页
  自己会拉 OBS，不构成反证）

只要第一行，第二行是交叉验证；两行都要标注在 App 里看的。

## 已排除的假设

区分两栏：**实测排除** 是有可复现的对照；**单次未复现** 只是改完看了一次。

| 假设 | 改动 | 结果 | 强度 |
|---|---|---|---|
| `flag` 全同导致画不出线 | 改成 `p.time_ms` 逐点递增 | 仍无线 | 单次未复现，见下节 |
| `bdA` 恒 1.0 无海拔特征 | 改成平滑缓坡 | 仍无线 | 单次未复现，见下节 |
| OBS 键少了 `step_json` | 对 `RunData` 建表语句，11 键是对的 | 不是问题 | 实测排除 |
| `useZip` 应为 true | 手工重打包该记录验证 | 仍无线 | 单次未复现 |
| 轨迹没上传 | 从 OBS 下载并解压，423 点齐全 | 不是问题 | 实测排除 |
| objectKey 时区猜错 | 旧版本地时区+UTC 各传一份 | 仍无线 | **单次未复现，本次重做** |

最后一条要注意：旧版的坑不在「各传一份」这个策略，而在**旧版两次运行取到了不同时区**
（11-07 那批只传了 UTC，10 月那批只传了 UTC+8 的 rrid 路径），所以单条记录可能只有
一个 key 命中、也可能一个都不中。新版固定 `8 * 3600` 并把 UTC 版与 rrid 路径一起传，
三条都命中——这一条是实测的（GET 200 × 3）。

`RunData` 表的 11 个键（`extension_json` 在里面，不用删）：

```sql
CREATE TABLE `RunData` (
  rrid, uuid, uid, run_data, step_freq_json, speed_json, segment_json,
  fixed_point_json, runFaceCheck, type, upload_success, timestamp, file,
  laps_json, runId, extension_json, isUploadSuccess
)
```

## 附：OBS 对象的结构（下载实测，2026-11-12）

`/api/obs/fetch` 换签名下载回来的是一层包装，不是直接的点数组：

```
{rrid, uuid, uid, run_data, fixed_point_json, segment_json,
 speed_json, step_freq_json, laps_json, extension_json, runFaceCheck}
```

**`run_data` 是 base64(gzip(JSON))**，解开是：

```json
{"allLocJson": "[{...406 个点...}]", "useZip": false}
```

也就是说轨迹点确实在 OBS 里，只是藏在 `run_data` 这一层里，不是顶层
字段。详情接口回的 `allLocJson: null` 指的是**它自己不回**，不是服务端没存。

各字段实测（rrid `1362680775`，2026-11-12 04:37，pace 刷的）：

| 字段 | 内容 | 备注 |
|---|---|---|
| `run_data` | gzip，内含 406 个点 | `useZip` 字段却是 `false` |
| `fixed_point_json` | `{"fivePointJson": "[...5 个点...]"}` | 有 `isPass/position/flag` |
| `speed_json` | 1s 一个桶，含 distance/beginTime/endTime | 有内容 |
| `step_freq_json` | 1s 一个桶，含 stepsNum/beginTime/endTime | 有内容 |
| `laps_json` | 每公里一圈，含 avgCadence/avgPace/avgStride | 有内容 |
| `segment_json` | **`[]` 空数组** | 可疑 |
| `extension_json` | **空串** | 可疑 |
| `runFaceCheck` | **空串** | 可疑 |

轨迹点本身没问题：406 个点、`flag` 406 个互不相同且严格递增、`lat/lng`
是真实 BD-09 坐标、28 个字段齐全。

**所以现在的问题精确定位到「三个空字段 + useZip=false」**，而不是轨迹本身。
缺真机样本做对照，账号里 20 条全是刷的。

## 附：真实轨迹对象长什么样（从 OBS 下载的实测）

拿 `1360341003`（Neko 刷的）走 `/api/obs/temporary/url` 换签名下载，解 gzip 后
422～425 点，逐点统计字段分布：

| 字段 | 实测 | 备注 |
|---|---|---|
| `flag` | **全条相同** | 等于整条跑步的**开始时间戳**（毫秒），不是逐点采样时刻 |
| `coorType` | `"gcj02"` | 字符串 |
| `lat` / `lng` | BD-09 真实坐标 | 不是 -1 占位 |
| `gLat` / `gLng` | GCJ-02 真实坐标 | 与上面那对各自独立 |
| `bdA` | 恒 `1.0` | 海拔，全程无变化 |
| `bdD` | 恒 `0.0` | 方向角 |
| `bdS` | 恒 `1.0` | 速度 |
| `count` | 恒 `1` | |
| `gainTime` | `""` | 空串 |
| `dtr` | `0.0` | |
| `locType` | `1` | |

只有这一组值，没有第二份样本可比。但它已经能说明两件事，而且**都是格式层面的，
不涉及 App 会不会画线**：

**一、「flag 全同导致画不出线」这个假设没有依据。** 真实记录的 `flag` 本来就
是全同的。本工具现在写的是 `p.time_ms`（逐点递增），反而跟真实数据不一致。
`submit.rs` 里那段注释（「全部相等等于所有点同时定位，折线拿不到时间维度的
信息」）是推的，不是测的——它把「flag 相同」和「点同时定位」等同了，而真实
数据里两者并存（flag 相同 + 每点各自的 `gLat/gLng` 不同）。

**二、真实记录比本工具「更假」。** 海拔恒 1.0、方向恒 0.0、速度恒 1.0，
本工具给了平滑缓坡、真实方向角和逐点速度。这两项都改过、都「仍无线」，
但它们不构成排除——见上表「单次未复现」那一栏。

**所以 `flag` 和 `bdA/bdD/bdS` 这两条，既没被证明是原因，也没被证明不是。**
要收口还是得做下面的对照实验，不是继续调字段。

**待定的一步**：要不要把 `flag` 改回全同（对齐真实格式）。现在的增序版本是
「为了对齐 App 排序逻辑」猜的，而唯一的真实样本是全同。改不改都不影响服务端
判定（`verify_view` 从首点反解开始时间，两种写法都能过）。

## 若要在 App 里必定有线：写本地库

需要往 `/data/data/com.zjwh.android_wh_physicalfitness/` 写 Room 记录 + 加密轨迹文件。
实测过的路径：

| 路径 | 结果 |
|---|---|
| Shizuku/adb shell 写 app 私有目录 | `Permission denied`，shell 域（uid=2000）进不了 `app_data_file` |
| `su -c` 提权 | `[POLICY_BLOCKED]`，设备无 root |
| `appops set android:mock_location allow` | `[POLICY_BLOCKED]`，不在白名单 |
| 伪造 GPS 让 App 自己跑一条 | 依赖上一条，开不了 mock location |
| App 自带导入（gpx/kml/importRun） | 不存在，全项目零命中 |
| 降级到老版本 App | 未验证。老版本可能走 `jsonFromObs=0` 直接读服务端，但服务端有强制更新检查 |
| 重打包 App 改判断 | 签名一变装不上 |

## 附：真机记录为什么一直有线

因为它在手机上跑过，本地库和轨迹文件都在。换台手机登录，自己真跑过的记录同样会
变成空地图——分界线是**这台手机上有没有那份文件**，不是记录是不是刷的。
