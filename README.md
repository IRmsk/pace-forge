# pace-forge

**运动世界校园 自动刷跑客户端** — 纯 Rust，一条命令跑完登录到提交。

> 针对 **7.4.01** 实测。CLI + Web 双模式，不用装 App、不用模拟点击、不用真机跑。
> 版本号是硬编码的，厂商换版本需要重新对齐（见「已知局限」）。

```bash
pace-forge run 2 12      # 跑 2 公里 / 12 分钟，直接提交
pace-forge web           # 或者开网页，点一下就跑
```

---

## 记分跑

**记分跑 = `runMode=1` 校园跑**，是计入体育课成绩的那种。和自由跑的区别：

| | 记分跑 | 自由跑 |
|---|---|---|
| 接口 | `runMode=1` | `runMode=2/3` |
| 时段 | **有固定时段**，不在时段内报 `11016` | 无限制 |
| 打卡点 | 必须全过 | 无 |
| 围栏 | 必须在校区内 | 无 |
| 学期目标 | 有（`semesterDis` / `selDistance`） | 无 |

刷记分跑前先查学期进度：

```bash
pace-forge semester        # 看还差多少公里 / 几次
pace-forge run 2 12        # 在有效时段内提交
```

`selDistance` 用的是**规则给的最小里程**，不是你自己设的目标——填错会被驳回。

## 它能做什么

| 步骤 | 说明 |
|---|---|
| ⓿ 查进度 | 学期累计里程 / 次数，知道还差多少 |
| ① 登录 | 极验 v4 全本地求解，不需要打码平台 |
| ② 拉策略 | `runModePolicy`，拿规则串和最小里程 |
| ③ 选围栏 | 多校区按定位锚点自动选对 |
| ④ 拉打卡点 | 必经点全部命中 |
| ⑤ 规划轨迹 | 闭环折线，凑到目标里程 |
| ⑥ 反推时间戳 | 由速度剖面算出每点时刻 |
| ⑦ 合成步数 | 步频 / 步幅 / 10 秒分桶 |
| ⑧ 自检 | 七大类检查，不过就不发 |
| ⑨ 上传明细 | OBS 对象存储 |
| ⑩ 提交成绩 | `runnings/save/record` |

Web 界面默认 `:9999`（`pace-forge web 0.0.0.0:9999`）：登录、记录列表、轨迹地图、模式切换、自检结果实时显示。

## 为什么这个能过

市面上流通的实现大多只做到「报文能发出去」，数据本身经不起看。这三个问题是实测发现的：

### ① 步频、步数、速度三者打架

服务端拿 `totalSteps / totalTime` 和 `totalDis / totalTime` 一除，就能反推你声明的步频，跟配速对不上就驳回。

常见的 `150 + 12v` 公式在 6:40/km 会给出 180 步/分，真实数据只有 144——差 36 步，而且**形态是反的**：

| 配速 | 实测步频 | 正确公式 | 拍脑袋公式 |
|------|---------|---------|-----------|
| 5:31/km | 170 | 169 | 173 |
| 6:40/km | 144 | 146 | 180 |
| 7:02/km | 139 | 140 | 177 |
| 8:19/km | 125 | 124 | 162 |

慢配速时步频掉得更快，是**步幅主导**而不是步频主导。pace-forge 用的关系式由下面 4 组样本拟合得出：

> ⚠️ **样本量说明**：n=4 的一元线性回归只剩 2 个自由度，残差标准差和 R² 都没有统计意义。
> 这条公式是**基于 4 个点的拟合与推测**，不是经过验证的规律。它的价值在于「比常见的
> `150+12v` 形态正确」，而不在于精确。要当成结论用，需要补到 30 份以上真实记录。

```
步频(步/分) ≈ 34.4 + 44.5 × 速度(m/s)
```

并写成硬约束，误差 < 1e-9：

```
v = (cadence / 60) × stride
```

### ② 10 秒分桶是白噪声

`stepsPerTenSec` 如果用均匀随机数抖，相邻桶互相独立——一阶自相关 0.089，这是随机数的指纹。真人步频有惯性，自相关显著为正。

用 Ornstein-Uhlenbeck 过程做均值回归：

```
c_{t+1} = c_t + θ(target_t − c_t)·Δt + σ·√Δt·Z,   Z ~ N(0,1)
```

对比（`0.089` 是均匀随机生成器的理论值，`0.569` 来自少量真人记录的估算，样本不足以给出置信区间）：

| 方案 | 标准差 | 相邻差 | 一阶自相关 |
|---|---:|---:|---:|
| 均匀随机 | 3.36 | 3.66 | **0.089** ← 随机数指纹 |
| OU 均值回归 | 2.01 | 1.42 | **0.569** ← 真人量级 |

θ=0.07 对应相关时间约 14 秒，桶间隔 10 秒时相关性还有 0.5。

**这里的自相关是真的有测试守着的**：`lag1_autocorr()` 按标准定义算
`r1 = Σ(x[i]-μ)(x[i+1]-μ) / Σ(x[i]-μ)²`，测试要求生成结果高于白噪声上界 `2/√n`，
并用一条反向测试确认纯白噪声会被判为无相关。

### ③ 时间戳和速度对不上

如果点位等距、时间戳也等距，等于全程匀速；但报文里的 `speedPerTenSec` 有起伏，两者放在一起自相矛盾。

正确关系是 `dt_i = d_i / v_i`：速度快的段用时短。总时长用**最大余数法**分配，`Σdt` 从构造上精确等于目标，不存在累积舍入误差。

实测偏差：

```
剖面速度 vs 实测速度：平均 0.23%，最大 0.49%
分桶速度 vs 桶内实测：最大 0.00%
总时长误差：0 ms
```

## 速度剖面是物理的

不是恒定配速，也不是纯随机波动：

- **起跑热身**：前 20 秒从 0.85× 匀速 ramp 到 1.0×
- **中段起伏**：OU 均值回归
- **弯道预判**：`v² ≤ v_corner² + 2·b·d`，提前 40m 以 1.5 m/s² 收速
- **终点冲刺**：最后 150m 线性提速 12%

全程匀速跑完是最容易识别的机器特征之一。

> 关于弯道减速：400m 标准跑道内圈半径 36.8m，2.8 m/s 配速过弯的向心加速度只有 0.198 m/s²，远低于人体上限（约 2.5 m/s²）——**这个配速本来就不需要减速**。弯道限速只在速度 >4 m/s 或半径 <10m 的急弯实际生效。

## 两种路线模式

### 自由路线

在定位锚点周围生成闭环折线，自动凑到目标里程，必经打卡点全部穿过。

### 操场绕圈

按 World Athletics 标准 400m 跑道建模：

```
        ┌──────────────────────┐
       ╱                        ╲
      │   直道 84.39m            │     弯道半径 36.50m
       ╲                        ╱      半圆长 115.61m
        └──────────────────────┘

  一圈 = 84.39×2 + 115.61×2 = 400.00m
```

支持 1–8 道（每道宽 1.22m）。实测：

| 道次 | 圈长 | 生成 5 圈 | 闭合误差 | 弯道曲率 |
|---|---:|---:|---:|---:|
| 第 1 道 | 400.0m | 1999.1m | 0.00m | 0.02719 |
| 第 2 道 | 407.7m | 2037.5m | 0.00m | 0.02632 |
| 第 4 道 | 423.0m | 2114.2m | 0.00m | — |

理论曲率 `1/36.8 = 0.02717`，实测 0.02719。直道曲率 0.00000。

## 提交前自检

**宁可本地失败，也不要把注定被驳回的报文发出去。** 驳回会记错误次数，异常多了触发风控，连正常提交都会被拦。

七大类，分三级：

| 检查项 | 等级 | 内容 |
|---|---|---|
| 时间轴 | 致命 | 起止戳缺失、顺序颠倒、跨度与 `totalTime` 不符 |
| 轨迹时间 | 致命 | 首末点没落在报文边界、时间戳非严格递增 |
| 里程 | 致命 | 折线实测与声明差 >2m |
| 坐标 | 致命 | 越界 / (0,0) / 相邻跳变 >200m |
| 打卡点 | 致命 | 任一必过点最近距离 >0.5m |
| 分桶 | 致命 | 桶数不符、步数和不等于总步数 |
| 物理 | 致命/警告 | 配速超规则区间、步频超人体范围、步幅异常、步态不匹配 |

```bash
pace-forge dry 2 12      # 只走自检，不发任何写请求
```

## 反检测

7.4.01 在客户端本地加了一层校验，`pace-forge` 会先自己过一遍。

### 点位打分

7.4.01 新增的 `libswsport.so` 里有个 `isValidPoint`，**不是布尔判断，是打分**：

```
score = 基础分(点位等级) + 模式分 + 距离分 + 时间分
valid = (标志A == 0) && (标志B != 0) && (score > 65)
```

各项上限：基础 30、模式 30、距离 30、时间 10，满分 80。
要过 65 分，**基础分必须 ≥ 25**，也就是点位等级要够高——不是随便一个点都算数。

距离分的关键阈值是 **10 米**：相邻点间距低于 10 米才拿满分。

`pace-forge` 默认采样 5 米一个点，所以满分区占比 100%：

```
$ pace-forge check 2 12
=== 点位体检（模拟 7.4.01 本地规则）===
  点位检查通过 · 满分区 100.0% · 平均间距 5.0m
  判定: ✓ 通过
```

间距超过 10 米只扣分，超过 20 米直接拦截——因为那已经不是"跑步采样稀疏"，是"轨迹断了"。

### 心率字段

7.4.01 **移除了** `BODY_SENSORS` 权限，不再读心率。所以报文里如果还带心率，
反而是"用旧版本伪造"的信号。提交前会自动剔除：

```rust
pub const FORBIDDEN_FIELDS: &[&str] = &[
    "heartRate", "heartRates", "hrData",
    "avgHeartRate", "maxHeartRate", "bodySensors",
];
```

### 硬件指纹

7.4.01 的 Manifest 把这三个设成 `required=true`（不满足就装不上）：

```
android.hardware.sensor.stepcounter    计步器
android.hardware.sensor.stepdetector   步伐检测
android.hardware.bluetooth             蓝牙
```

前两个是步数来源，第三个对应新增的 `getBluetoothInfo`（穿戴设备同步）。
纯软件方案不带这些，属于"设备指纹不全"，但服务端目前没有强制校验的证据。

## 使用

### 命令行

```bash
# 先登录（也可以在网页里登）
pace-forge web
# 打开 http://127.0.0.1:9999，输入手机号和密码

# 刷跑
pace-forge run 2 12        # 2 公里 / 12 分钟，提交前会问一次
pace-forge run 3 18 -y     # 加 -y 跳过确认

# 只预演
pace-forge dry 2 12

# 操场参数
pace-forge stadium 5 2     # 第 2 道跑 5 圈
```

### Web 界面

```bash
pace-forge web 0.0.0.0:9999
```

登录 → 记录列表 → 轨迹地图 → 设置里程时长 → 点「生成」看自检结果 → 点「提交」。

### 作为库

```rust
use pace_forge::track::{plan, retime, simulate, inspect, Check, PlanRequest, SimParams};

let track = plan(&req, &mut rng)?;                                    // ① 规划
let (times, _, len) = retime(&xy, 720, start_ms, seed, &KinParams::default(), 1.0, 8.0);  // ② 定时
let sim = simulate(&timed, &SimParams {                               // ③ 合成
    total_distance_m: len as f64,
    total_sec: 720,
    start_ms,
    target_steps: None,
    seed,
    ..Default::default()
})?;

let report = inspect(&check);                                         // ④ 自检
if report.blocked() {
    eprintln!("{}", report.summary());
}
```

## 协议要点

几个容易踩的坑，都是实测确认的：

**信封**：`{"d","h","k","p":"101","t":"0"}`。RSA-1024 加密 AES 密钥，AES-128-CBC 用**全零 IV**，密钥派生是三段自定义函数（`byte_hash` → `feistel_transform` → `final_mix`）。

**速度字段**：`speed = 配速(分/公里) × 1000`，不是 m/s × 1000。用 `speedTop=2.0 / speedBottom=10.0` 反推确认。

**点位接口**：`runec` 字段是额外一层信封，外层顺序 `k,p,d,h,t`（不是标准体的 `d,h,k,p,t`）；`sign = MD5(http版URL + 盐)`，注意是 **http://** 不是 https://；限流 5 分钟 3 次。

**OBS 上传**：`method` 参数是 `"Put"` 首字母大写，不是 `"PUT"`。

**静默窗口**：提交后 600 秒内不能再发跑步请求，否则判异常。

## 登录失败排查

登录是最容易卡住的一步，绝大多数失败都能从**错误码**直接定位。先看服务端返回的 `error` 值（Web 界面会原样显示，CLI 会打在 stderr）：

### 10121 · 此账号已在其他设备登录

```
10121 登录失败，此账号已在其他设备登录，因账号保护机制，原状态未退出；
请过一小时后登录或原设备退出后再登录
```

服务端按 `device_id` 认设备。同一个账号每次登录必须用**同一个** device_id，否则它认为你在换手机，直接锁号一小时。

本项目按「手机号」做作用域，一个账号有且只有一套 device_id，存在 `~/.pace-forge-device-id-<hash>`。会触发这个错误的情况：

- 之前用过别的同类工具，它给账号挂了另一个 device_id
- 手动删过 `~/.pace-forge-device-id*` 文件
- 用同一个账号在手机 App 和本工具之间来回登录

**处理**：等满一小时再试。如果反复触发，去手机 App 里主动退出登录，让它清掉旧会话，再回来登录。

注意：**锁定期内每次重试都会重新计时**，越试越久。等就行，别刷。

### 需要过极验滑块

极验 v4 是本地求解（Canny 边缘 + NCC 匹配 + PoW），不需要打码平台。如果反复失败：

- 检查出口 IP。机房 / 公共代理的 IP 会被极验直接判风险，换成家宽
- 网络抖动导致 challenge 过期。重试即可
- 出口走了透明代理（Clash TUN 之类）时，`run.gxapp.iydsj.com` 的 TLS 指纹可能被改，直连或加规则绕开

### 连接失败 / Connect error

不是账号问题，是本机到 `run.gxapp.iydsj.com` 不通。先确认：

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://run.gxapp.iydsj.com/
```

通不了就是网络层的事（代理、DNS、防火墙），和本项目无关。

### 拉数据失败但登录成功

登录成功、后面某一步失败，通常是**接口限流**。打卡点接口限「前 5 分钟内最多 3 次」（错误码 `10603`），本项目带 5 分钟缓存，正常用不会碰到。如果手快连点，等 5 分钟。

### 其他错误码

把完整错误贴到 Issue 里，包括 `error=` 后面的数字和 message。只写「登录不进去」没法定位——`10121`（设备锁）、`10603`（限流）、密码错、极验失败，处理方式完全不同。

**另外请带上**：操作系统、`pace-forge --version`、用的是 Web 还是 CLI、有没有挂代理。
